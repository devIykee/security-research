Introduction 
Enhanced is a structured-product infrastructure for onchain assets, including real-world assets (RWAs). In v1, the system allows users to write options such as covered calls and cash-secured puts onchain, as well as a vault infrastructure that enables the rolling of these strategies. 
The core consists of 2 main components: an options engine allowing request-for-quote (RFQ) where users can write options onchain directly, and automated vaults, which pool depositor capital and execute through the same engine. Both resolve to identical minting, collateral, and settlement logic. 
The protocol builds on a battle-tested onchain options protocol, adding a signed RFQ auction, the rolling vault layer, and improved modular access controls. 
For the vault, the design innovates to align with the user's favor. In a first for options vault products, premiums can accrue to a separately withdrawable balance — income can be taken every epoch without touching principal. Parameters such as epoch cadence and fees are fully configurable by the vault owner. Options are written via auction to competing institutional market makers rather than priced by a single desk — allowing better price discovery, resulting in better premiums reaching the user. 
Enhanced v1 is an onchain system that opens up more possibilities for structured payouts and strategies to come.

Issue H-1: Physical-settlement payout depends on writer settlement order when multiple writers share an oToken [RESOLVED] 
Source: 
https://github.com/sherlock-audit/2026-05-enhanced-may-26th-2026/issues/80 
Summary 
Physically settled positions share per-oToken redemption balances (collateral, receiving asset, oToken quantity), and each writer's settlement is computed against whatever remains in those balances at the moment they settle. Because the oToken is keyed only by option-series parameters, multiple writers of the same series share one oToken and one pooled set of balances. When buyers only partially exercise, the remaining balances are a mix of collateral and strike asset, and the order in which writers settle determines how much of each asset they receive. Writers with identical positions can receive materially different value. 
Vulnerability Detail 
The oToken address is resolved purely from the option series:

otoken.strikeAsset,

otoken.strike, 
otoken.expiration,

There is no vault-owner component, so any writer minting the same series writes the same oToken and shares its redemption balances. 
handleSettle then distributes the shared balances per writer based on the live balances. The strike asset is paid out first-come, and the collateral share is computed against the current (shrinking) totals:

The first writer to settle absorbs the available strike asset; later writers settle against the depleted strike balance and receive proportionally more collateral. When the strike asset and the collateral have diverged in value (the normal ITM case), this is not value-neutral. 
Worked example (CALL, underlying = collateral = WETH, strike = 1000, expiry price = 2000, two writers each minted 5 oTokens): 
Initial shared balances: collateral = 10 WETH, receivingAsset = 0, otokenQty = 10e8. Four buyers exercise during the redeem window, each paying 1000 USDC into the pool and taking 1 WETH: 
collateral = 6 WETH, receivingAsset = 4000 USDC, otokenQty = 10e8
	



First settlement (writer A, 5 oTokens): strikePayout = 1000 * 5 = 5000 > 4000 (scenario 2). Takes all 4000 USDC (strikeCount = 4), collateral share = 6 * (5-4) / (10-4) = 1 WETH. Writer A receives 4000 USDC + 1 WETH = $6,000. Remaining: collateral = 5 WETH, receivingAsset = 0, otokenQty = 5e8. 
Second settlement (writer B, 5 oTokens): receivingAsset = 0 (scenario 1). Collateral share = 5 * 5 / 5 = 5 WETH. Writer B receives 5 WETH = $10,000. 
Both writers held identical positions, but A receives $6,000 and B receives $10,000 purely because of settlement order. The fair pro-rata split of the 6 WETH + 4000 USDC remaining (= $16,000) would be $8,000 each. 
Impact 
When multiple writers share an oToken series and buyers exercise only partially, settlement is not pro-rata: the writer(s) who settle first are forced to take the less valuable mix of assets, and later writers receive the more valuable mix. This is a value transfer between writers driven by transaction ordering, not by their actual positions, and can amount to a significant fraction of a writer's payout (about 25% in the example). It is a fairness/loss issue between users rather than a drain of protocol funds, and it requires multiple writers of the same series plus partial exercise.

Issue M-3: Ghost initialAmountTotal permanently blocks re-entry after losses [RESOLVED] 
Source: 
https://github.com/sherlock-audit/2026-05-enhanced-may-26th-2026/issues/47 
Summary 
initialAmountTotal accumulates every deposit but is only decremented by actual withdrawals — losses are never subtracted. After a user suffers losses and exits, a residue equal to total losses persists in initialAmountTotal. Any future re-deposit is evaluated against this inflated denominator, making re-entry require a fresh deposit equal in size to all prior losses. 
Vulnerability Detail 
initialAmountTotal is incremented on deposit and decremented only when funds are physically withdrawn: 
// EnhancedVault.sol:537 
fund.initialAmountTotal += amount; // on deposit 
// EnhancedVault.sol:564, 595, 721 
fund.initialAmountTotal -= rec.amount; // on withdrawal
	



When a user suffers losses, those losses are never subtracted from initialAmountTotal. After a full exit, the ghost residue remains. 
Concrete example (as described in bugs.md): 
• Alice deposits 1000 USDC. initialAmountTotal = 1000. 
• 60% loss. Alice's principal = 400. Ratio = 40% < 50% threshold → ejected. • Alice withdraws 400 USDC. initialAmountTotal = 1000 - 400 = 600 (loss residue). • Alice tries to re-enter with 100 USDC. initialAmountTotal = 700. 
• Ratio = 100/700 = 14.3% < 50% → ejected immediately. 
• Required re-entry deposit to reach 50%: Y / (600 + Y) >= 0.5 → Y >= 600 USDC. Alice must deposit an amount equal to her entire historical losses just to re-enter. 
Impact 
Users who suffered losses and exited are permanently penalized on re-entry. The required deposit scales with historical losses, not current vault risk. This is not disclosed 
12
to users and creates an undocumented barrier to participation. 
Code Snippet

// After full exit, ghost residue = total losses

// no subtraction for losses
	



Tool Used 
Manual Review 
Recommendation 
When a user's position is settled at a loss (collateralRatio < 1), subtract the loss amount from initialAmountTotal: fund.initialAmountTotal -= (activePrincipal - settledActi ve). This ensures the denominator reflects actual invested capital, not historical deposits.

3. the taker confirms the actual execution quantity and signs the confirmation; 4. the maker-side payer approves the payment, signs the payment authorization, and grants the required authorization; 
5. the completed order package is submitted to the platform backend/operator; 6. the backend/operator performs final validation and submits the on-chain trans action. 
Therefore, an old maker quote cannot be executed by itself. The report assumes a per missionless stale-quote execution path, but such a path does not exist. Execution re quires the later taker confirmation, maker-side payer approval/signature/authoriza tion, nonce consumption, and operator-side validation. 
For this reason, validUntil is not enforced as an unconditional on-chain expiry check. Stale-quote handling is part of the platform/operator validation policy over the com plete order package, not a standalone on-chain check against the maker quote times tamp. 
Adding require(block.timestamp <= quote.validUntil) would be a product-policy change to the execution workflow, not a vulnerability fix.

Issue M-7: Unbatched deferred-queue flush bricks cycle advancement [RESOLVED] 
Source: 
https://github.com/sherlock-audit/2026-05-enhanced-may-26th-2026/issues/79 
Summary 
Users who request a withdraw while a vault is in SETTLED or PROCESSING_DONE are added to an unbounded _deferredQueueUsers list. startNextCycle flushes the whole list in one loop and re-enqueues every user, at about 46k gas each. Past a few hundred users this exceeds the per-transaction gas cap, so startNextCycle can never be included and the vault is stuck in PROCESSING_DONE, unable to start a new cycle. Principal is not lost: the vault can be force-ended via endVault, which uses a cheaper flush and lets users reclaim funds. 
Vulnerability Detail 
The flush cost is linear in the queue size, and the startNextCycle path uses the expensive enqueueUsers = true branch:

uint256 deferredLen = deferredUsers.length; 
for (uint256 i; i < deferredLen;) { 
address user = deferredUsers[i]; 
_deferredQueued[vaultHash][user] = false; 
if (enqueueUsers) _enqueueUser(vaultHash, user); 
unchecked { ++i; } 
}

EIP-7825 caps a single transaction at 2^24 = 16,777,216 gas. A Foundry PoC measures startNextCycle and shows it crosses that cap at roughly 362 deferred users:

200 9,276,966 yes 
300 13,894,566 yes 
400 18,512,166 no 
25
Deferred users N startNextCycle gas Within 16,777,216 cap 
1000 46,217,766 no 
The queue grows permissionlessly (one entry per withdraw request), so the threshold is reachable organically on a popular vault or by an actor with a few hundred funded positions. On a chain without EIP-7825 the ceiling is the block gas limit (~30M) and the threshold rises to about 700 users, but the vault still bricks. 
endVault flushes the same queue with enqueueUsers = false, so it skips the re-enqueue and stays cheap but still traverses the whole array.
